# Аварийный регламент: что делать, когда сломалось

**Возьмите копию этого файла заранее — читать его придётся тогда, когда кабинет не открывается.** В кабинете зайдите в раздел «Документация» и нажмите кнопку **«Скачать всё одним файлом»** (она же — прямая ссылка `https://reports.iig.ru/download/docs.md`, доступна любому вошедшему, включая наблюдателя и специалиста). Скачается файл `iig-reporter-docs-ГГГГ-ММ-ДД.md` со всеми документами комплекта и живой справкой по серверу. Сохраните его на телефон и в облако. В первой строке файла стоит дата выгрузки: **копия старше двух недель — сигнал скачать свежую**, потому что за две недели в системе успевают поменяться пути, команды и разделы кабинета.

Этот документ для того, кто прямо сейчас обнаружил, что что-то не работает, — не обязательно для Дениса и не обязательно днём: после него вы сможете за несколько минут понять, что именно сломалось, починить это сами по шагам или точно назвать, кому звонить и что говорить.

> **Половина «отказов» отказами не является.** Фоновые задачи в этой системе тикают на живом трафике: пока в кабинет никто не заходит, они не идут. «Не было копии базы за сегодня», «не пришла понедельничная сводка», «бюджеты не обновились» чаще всего означают «в кабинет никто не заходил», а не «сломалось». Подробности — в разделе 2.

> **Тишина ничего не доказывает.** Внешняя проверка живости пишет тревогу в Telegram только админам, у которых привязан личный чат с ботом, и только после двух неудач подряд — то есть примерно через 10 минут после падения (`iigbot/sysinfo.py`, `watch_once`, `fails_to_alert=2`). Если тревоги не было — это не значит, что всё в порядке.

## 1. Первые три минуты

Делайте по порядку, не пропуская. Каждый шаг — 10–20 секунд.

**Шаг 1. Откройте с телефона (не с того же компьютера, не с того же Wi-Fi):**

```
https://reports.iig.ru/healthz
```

Это публичная страница, вход не нужен. Она возвращает короткий JSON.

| Что видите | Что это значит | Куда дальше |
|---|---|---|
| `{"ok": true, "version": "…", "uptime": "…"}` | Приложение живо и база отвечает. Проблема у вас (сеть, браузер, сессия) либо в конкретной функции, а не в кабинете целиком | Раздел 2, ветка «кабинет отвечает» |
| `{"ok": false, …}` (HTTP 503) | Приложение поднялось, но **база не отвечает**. Это единственный случай, когда `/healthz` отдаёт not-ok | Раздел 8 и Процедура 3 (раздел 11) |
| Ошибка 500, «Internal Server Error», страница Passenger | Приложение не стартует — почти всегда синтаксис в свежезалитом файле или пропавшая зависимость | Раздел 4, строка «500 после выката» |
| Ничего не грузится, таймаут, «сайт недоступен» | Лежит хостинг, домен или ваш интернет | Раздел 4, первые две строки |
| Страница-заглушка хостинга | Аккаунт хостинга приостановлен | Раздел 15 — это не чинится технически |

**Шаг 2. Проверьте бота.** В любом рабочем чате с ботом отправьте `/whereami`. Ответил — вебхук жив. Молчит — раздел 5.

**Шаг 3. Посмотрите, что сломалось: всё или одно.** Если и кабинет, и бот, и таблицы — идите по разделу 2 сверху. Если одно из трёх — сразу в нужную таблицу.

**Шаг 4. Запишите время.** Заведите строку в журнале инцидентов (раздел 15) прямо сейчас, до починки: потом момент начала никто не вспомнит.

### Как вообще выполнять команды на этом сервере

Половина процедур ниже требует SSH-доступа к Beget. Простое `python -m iigbot …` там **не работает**: Passenger запускается системным Python, а библиотеки лежат в отдельном venv. Рабочий вид команды — вот такой, одной строкой:

```
cd ~/reports.iig.ru/public_html/_app/app && PYTHONPATH=/home/a/adolmax0/reports.iig.ru/public_html/_app/venv/lib/python3.10/site-packages /usr/bin/python3 -m iigbot <команда>
```

Дальше в документе для краткости пишется `<ПРЕФИКС> <команда>` — подставляйте всю строку выше. Источник: `app/deploy/DEPLOY-beget.md`, раздел «Еженедельная рассылка».

> Если SSH у вас нет — это нормально, доступ есть только у одного человека. Все места, где он нужен, помечены значком **[SSH]**. Дойдя до такого шага, останавливайтесь и звоните (раздел 14).

## 2. Развилка: что именно сломалось

Система состоит из четырёх кусков, которые ломаются независимо и чинятся по-разному.

| Кусок | Где живёт | Как проверить за 15 секунд | Если лежит — что ещё перестаёт работать |
|---|---|---|---|
| **Кабинет** (Flask под Passenger) | Beget, `~/reports.iig.ru/public_html/` | `/healthz` отдаёт 200 | Не отправить отчёт кнопкой, не посмотреть бюджеты, не открыть Контроль. Плюс встают **все** фоновые задачи — они тикают из кабинета |
| **Бот Telegram** (вебхук) | тот же процесс кабинета, маршрут `/tg/webhook` | `/whereami` в любом чате | Не приходят команды от клиентов, не работает привязка чатов. Отправка отчётов при этом идёт — она не через вебхук |
| **Яндекс** (Директ + Метрика) | облако Яндекса, один OAuth-токен на всё | `<ПРЕФИКС> gsheets-sync --check` | Разом: отчёты, бюджеты, цели, синхронизация клиентов, ночные Google-таблицы. **Токен один на пять API** — если «встало всё сразу», причина почти всегда здесь |
| **Google-таблицы** (ночная выгрузка) | **GitHub Actions**, не Beget | вкладка Actions в репозитории `github.com/trutnevde/IIG-auto-reporter` | Только таблицы клиентов. Кабинет и рассылка не затронуты |

### Фоновые задачи и почему их «отсутствие» — не поломка

Планировщик встроен в кабинет и запускается на каждом входящем запросе, но не чаще раза в 10 минут (`iigbot/web.py`, `_periodic_tick`, вызов из `before_request`). Дальше он смотрит метки в таблице `kv` и запускает просроченное:

| Задача | Как часто | Метка в `kv` | Что делает |
|---|---|---|---|
| `autosync` | раз в 20 ч | `autosync_last` | Тянет список клиентов Директа, цели Метрики, проверяет целостность базы |
| `budgets` | раз в 12 ч | `budgets_last` | Собирает остатки по бюджетам и **шлёт алерты в личные чаты** |
| `dialog_alert` | раз в 3 ч | `dialog_alert_last` | Уведомления «клиент ждёт ответа больше суток» |
| `backup` | раз в 24 ч | `backup_last` | Копия базы в `backups/`, ротация 14 штук |
| `digest` | понедельник с 10:00, не чаще раза в 5 дней | `digest_last` | Понедельничная сводка работодателю **в Telegram** |

Следствие: если в кабинет три дня никто не заходил, ни одна из этих задач не отработала. Первый же вход всё догонит — разом, в одном процессе. Это выглядит как «кабинет завис на минуту» и поломкой не является.

Второе следствие, важное для аварии: **любой запуск кабинета с боевым `secrets.json` запускает эти задачи** — включая те, что пишут живым людям в Telegram. См. раздел 13.

## 4. Бот молчит, отчёты не ушли

Сначала различите два разных отказа: **бот не отвечает на команды** (сломан вебхук) и **отчёты не уехали клиентам** (сломалась рассылка). Это разные механизмы: рассылка ходит в Telegram напрямую, вебхук ей не нужен.

| Симптом | Вероятная причина | Что делать по шагам | Как проверить, что починилось |
|---|---|---|---|
| Бот не отвечает на `/whereami` ни в одном чате, кабинет при этом жив | Слетел вебхук или **разошёлся секрет**: `/tg/webhook` сверяет заголовок с ключом `tg_webhook_secret` в базе и на несовпадении молча отдаёт 403 — ни одной строки в журнале не появится | **[SSH]** 1. `<ПРЕФИКС> webhook info` — посмотреть URL и `last_error_message`. 2. `<ПРЕФИКС> webhook set https://reports.iig.ru/tg/webhook` — переустановить (секрет перегенерируется и запишется в базу) | `/whereami` в чате отвечает названием чата и привязкой |
| Бот замолчал сразу после того, как кто-то запустил программу на своём компьютере | **Конфликт 409.** Токен у агентства один, вебхук и long-polling взаимоисключающие. Локальный запуск бота или десктопного окна ломает боевого бота | 1. Найдите, кто запустил, и попросите закрыть. 2. **[SSH]** `<ПРЕФИКС> webhook set https://reports.iig.ru/tg/webhook` | `/whereami` отвечает; в `webhook info` пустой `last_error_message` |
| Бот отвечает в личке, но не в группе | Бота удалили из группы или сняли права | Добавить бота в группу заново. Затем в этой группе `/whereami` — он покажет, привязан ли чат | `/whereami` в группе отвечает и показывает привязку к нужному логину |
| В понедельник **никому** не ушёл отчёт, в «Отчёты → История» за этот день **ни одной строки** | Не отработала задача cron в панели Beget: сервер спал, задача снята, изменился путь | 1. Проверьте почту аккаунта хостинга — туда падает вывод задач cron. 2. **[SSH]** Прогоните вхолостую: `<ПРЕФИКС> weekly --dry` — увидите, сколько отчётов построилось бы. 3. Боевую доотправку делать **только из кабинета**, поимённо (см. следующую строку и раздел 13) | В Истории появились строки за нужный период со статусом «sent» |
| Отчёт ушёл части клиентов, у остальных статус «error» | Обрыв связи с Telegram или с Директом на середине прогона | В кабинете: «Отчёты» → окно прогресса → кнопка **«Переотправить недошедшим»** (`only_failed`). Она берёт список из **прошлого прогона в памяти этого процесса** — после перезапуска приложения список теряется, тогда шлите поимённо кнопкой «Отправить снова» в Истории | Строки «error» в Истории заменились на «sent» по тем же клиентам |
| Статус «skipped», причина «нет открута за 4 недели» | Это не ошибка: у клиента нет расхода, отчёт не строится намеренно | Ничего не чинить. Если расход есть, а система его не видит — раздел 6, ветка «Директ» | — |
| Статус «no_chat», причина «нет привязанного чата» | Проект есть, чат не привязан | Кабинет → «Привязки», привязать чат к логину. Или в самом чате `/bind <логин>` (админ) | В карточке клиента виден чат; `resend` даёт «sent» |
| Клиент в списке, но отчёт ему **вообще не готовится** | Он помечен как «Сторонний» (`delivery = external`) — такие намеренно исключены из бот-рассылки и доставляются вручную копипастом | Кабинет → «Сторонние» → собрать текст и вставить клиенту в его мессенджер | Клиент подтвердил получение |
| Нужно доотправить одному клиенту, а кабинет лежит | **Такой возможности нет.** Консольная команда `weekly` принимает только `--dry`, фильтра по логину у неё нет | Сначала поднять кабинет (разделы 3, 9–11), потом «Отправить снова» в Истории. Запускать `weekly` без `--dry`, чтобы «добить одного», нельзя — уйдут дубли всем | — |

> **История в кабинете показывает последние 100 записей и не фильтруется.** При нынешнем объёме это примерно две недели. Разбор жалобы «отчёта не было три недели назад» из кабинета невозможен — нужен запрос к таблице `send_log` на сервере.

## 5. Клиент говорит, что не получил отчёт

Сквозная цепочка. Идите строго по порядку и останавливайтесь на первом «нет» — дальше проверять бессмысленно.

**1. Клиент вообще заведён?** Кабинет → «Клиенты», поиск по названию или логину Директа. Нет в списке — отчёт и не мог уйти; заведите проект и привяжите чат.

**2. Какой у него способ доставки?** В карточке — «Доставка». Если **«Сторонний»**, отчёт клиенту не отправляет никто: система только готовит текст, а вставляет его специалист вручную. Это самая частая причина жалобы. Идите в «Сторонние», соберите и отправьте.

**3. Есть привязка чата — и к какому именно чату?** Кабинет → «Привязки». Ключевая тонкость: у одного клиента может быть **несколько чатов**, и бота могли добавить не в тот. Чтобы убедиться, что это тот самый чат, отправьте прямо в чате клиента команду `/whereami` — бот ответит названием чата и логином, к которому чат привязан.

**4. Был ли у клиента расход за последние 4 недели?** Если нет — отчёт не строится по замыслу, в Истории будет статус «skipped» с причиной «нет открута за 4 недели». Проверить расход: карточка клиента, либо «Бюджеты».

**5. Что в Истории?** «Отчёты» → «История» за нужный период. Возможные статусы:

| Статус | Что произошло | Что делать |
|---|---|---|
| `sent` | Сообщение принято Telegram и доставлено в чат | Смотрите шаг 6 — почти наверняка ушло не туда, куда клиент смотрит |
| `skipped` | Нет расхода за 4 недели | Ничего. Объяснить клиенту |
| `no_chat` | Проект есть, чат не привязан | Привязать чат, затем «Отправить снова» |
| `error` | Telegram или Директ ответили ошибкой; текст ошибки в той же строке | Прочитать текст. Чаще всего — бота удалили из чата. Добавить обратно, «Отправить снова» |
| **строки нет вовсе** | Прогон рассылки не состоялся, либо клиент не попал в список | Раздел 4, строка «в понедельник никому не ушло» |

**6. Если статус `sent`, а клиент не видит.** Значит, отчёт ушёл в другой чат. Проверьте: тот ли это чат (шаг 3, команда `/whereami`), не удалили ли бота из группы после отправки, не смотрит ли клиент в другую группу с похожим названием. Название чата в Истории — из нашей базы, а оно могло устареть; ориентируйтесь на ответ `/whereami`, а не на подпись в кабинете.

**7. Записи в Истории нет, а период старше двух недель.** История отдаёт только последние 100 строк. Дальше — только запросом к базе на сервере **[SSH]**, к таблице `send_log` (колонки `login`, `sent_at`, `period_from`, `period_to`, `status`, `error`).

## 7. Перевыпуск доступов: что делать, если ключ протух

Три ключа, три разных владельца, три разных места, куда класть новое значение. Значений в документе нет и быть не должно.

| Ключ | Где лежит сейчас | Что ломается без него | Как заменить |
|---|---|---|---|
| **OAuth-токен Яндекса** (Директ + Метрика) | `_app/secrets.json` на сервере, ключ `yandex_oauth_token`; **плюс** секрет `YANDEX_OAUTH_TOKEN` в настройках репозитория GitHub | Отчёты, бюджеты, цели, синхронизация клиентов, ночные таблицы — всё сразу | 1. Выпустить новый под тем же аккаунтом Яндекса, права — доступ к API Директа и чтение Метрики. 2. **[SSH]** Заменить значение в `secrets.json`, права файла `600`. 3. Заменить секрет в GitHub — **иначе ночные таблицы продолжат падать**. 4. Процедура 1 (перезапуск). 5. Проверить: `<ПРЕФИКС> gsheets-sync --check` |
| **Токен Telegram-бота** | `_app/secrets.json`, ключ `telegram_bot_token` | Бот и вся отправка отчётов | 1. Перевыпустить в BotFather. 2. **[SSH]** Заменить в `secrets.json`. 3. Процедура 1. 4. **Обязательно** переустановить вебхук: `<ПРЕФИКС> webhook set https://reports.iig.ru/tg/webhook`. 5. Проверить `/whereami` в чате |
| **Ключ сервисного аккаунта Google** | `_app/sa_key.json` на сервере; **плюс** секрет `GOOGLE_SA_KEY` в GitHub | Только Google-таблицы | 1. Новый ключ в консоли Google Cloud для того же сервисного аккаунта. 2. **[SSH]** Положить файл в `_app/`. 3. Заменить секрет в GitHub (содержимое JSON целиком). 4. Убедиться, что почта сервисного аккаунта по-прежнему имеет доступ к таблицам клиентов |
| **Секрет вебхука Telegram** | в базе, `kv.tg_webhook_secret` | Бот молчит, в журнале — ни одной ошибки | Не заменяется руками. Команда `webhook set` генерирует его сама и записывает в базу |

Что где лежит и когда менялось, видно админу в кабинете: «Сервер» → блок ключей. Значения там замаскированы, показывается только длина и хвост. Ключ, которому больше 180 дней, подсвечивается как просроченный.

> **ТРЕБУЕТ УТОЧНЕНИЯ У ДЕНИСА:** под каким аккаунтом Яндекса выпущен боевой токен и у кого есть доступ к этому аккаунту; кто владелец проекта Google и сервисного аккаунта; кто владеет ботом в BotFather; у кого, кроме Дениса, есть права на репозиторий GitHub и его секреты. Без ответов на эти четыре вопроса ни один ключ перевыпустить нельзя, и вся таблица выше нерабочая.

| Симптом | Вероятная причина | Что делать по шагам | Как проверить, что починилось |
|---|---|---|---|
| `/healthz` отдаёт 503, кабинет не открывается | Файл базы повреждён, недоступен или диск переполнен | 1. Сначала исключите место (строка ниже). 2. Затем **Процедура 3 (раздел 11)** | `/healthz` отдаёт 200 |

Это **уже починено** замком в `_SharedConn` (`iigbot/storage.py`); строки в журнале — историческое эхо | Если появляются свежие такие строки, зафиксируйте дату и передайте разработчику: значит, лечение перестало работать | В журнале нет новых записей этого вида |

Файл уйдёт в личный чат админа с ботом (его надо предварительно привязать в Настройках). Это ручная кнопка, её никто не нажимает по расписанию | В личном чате с ботом лежит файл `iigbot_ГГГГММДД_ЧЧММ.sqlite3` со свежей датой |

## 9. Процедура 1: перезапустить приложение

Самое частое и самое безобидное действие. Passenger следит за файлом `tmp/restart.txt` и поднимает приложение заново, как только файл меняется.

**Способ А — из кабинета (если он открывается).** Только админ. «Сервер» → кнопка **«Перезапустить приложение»**.

**Способ Б — по SSH [SSH].** Одна строка:

```
echo restart > ~/reports.iig.ru/public_html/tmp/restart.txt
```

**Способ В — по SFTP, без SSH.** Откройте `~/reports.iig.ru/public_html/tmp/`, скачайте `restart.txt`, измените в нём что угодно (хоть добавьте пробел) и залейте обратно. Файл-маркер, содержимое роли не играет.

**Проверка:** откройте `/healthz` — поле `uptime` должно обнулиться (секунды, минуты). Если оно по-прежнему показывает часы или дни — перезапуск не сработал, файл лежит не там: проверьте точный путь в кабинете, «Сервер» → «Пути».

**Что перезапуск делает и чего не делает.** Сбрасывает: кэш выгрузок Директа в памяти, счётчик неудачных входов, список «недошедших» из прошлого прогона рассылки, состояние идущих фоновых задач. **Не сбрасывает**: вход пользователей (ключ сессий постоянный, лежит в базе), метки планировщика, ничего в базе.

## 10. Процедура 2: откатить выкат

Когда применять: после заливки новых файлов кабинет отвечает 500 или ведёт себя явно не так, и вы не понимаете, что именно сломалось.

> **Откат возвращает только файлы приложения.** Схема базы не откатывается — миграции необратимы. Если сломанная версия успела добавить таблицу или колонку, они останутся. Обычно это безвредно, но знать надо.

**Способ А — из кабинета.** Только админ. «Сервер» → блок «Откатить выкат»: список снимков с датой, весом и перечнем файлов. Выбираете снимок, жмёте — система сначала складывает **текущие** файлы в папку `before_rollback_ГГГГММДД-ЧЧММСС` (то есть откат можно откатить), затем возвращает файлы из снимка и сама перезапускает приложение.

**Способ Б — руками по SFTP [SSH/SFTP], если кабинет не открывается.**

1. Зайдите в папку `deploy_backup` (точный путь — в кабинете «Сервер» → «Пути», строка «Копии файлов выката»; ищется вверх по дереву от папки приложения).
2. Выберите папку с нужной датой.
3. **Сначала** скопируйте текущие файлы из `_app/app/iigbot/` куда-нибудь рядом — на случай, если откат не поможет.
4. Скопируйте файлы из снимка в `_app/app/iigbot/`. Откат работает только с файлами верхнего уровня папки пакета, вложенные папки он не трогает.
5. Процедура 1 — перезапуск.

**Проверка:** `/healthz` отдаёт 200, и поле `version` показывает **прежнюю** версию. Затем откройте раздел кабинета, который сломался, и убедитесь, что он работает.

> **Внимание: папка `deploy_backup` и файл `iigbot/VERSION` в репозитории отсутствуют — их создаёт процедура выката, а она делается вручную.** Если выкат перестал класть снимки, откатывать будет нечего, и вы узнаете об этом ровно в тот момент, когда откат понадобится. **Проверьте прямо сейчас, не дожидаясь аварии:** кабинет → «Сервер» → блок «Откатить выкат». Если список пуст — откат недоступен, единственный путь восстановления кода это репозиторий GitHub.

> **ТРЕБУЕТ УТОЧНЕНИЯ У ДЕНИСА:** кто и чем наполняет `deploy_backup` и пишет `iigbot/VERSION` при выкате — скриптом, руками, или это не делается вовсе.

### Помните про два контура выката

Код едет в **два разных места**, и они не связаны:

| Куда | Чем | Что оттуда работает |
|---|---|---|
| Beget, `_app/app/iigbot/` | заливка по SFTP | Кабинет, бот, недельная рассылка, бюджеты |
| GitHub, ветка по умолчанию | `git push` | **Ночная выгрузка в Google-таблицы** — Actions делает `checkout` и запускает код из репозитория |

Следствия, которые больно кусают в аварии: правка, залитая по SFTP без коммита, до ночных таблиц не доедет; коммит без заливки, наоборот, изменит поведение ночной выгрузки, а кабинет останется прежним. И откат из `deploy_backup` откатывает **только Beget** — ночная выгрузка продолжит крутить то, что лежит в репозитории.

## 11. Процедура 3: восстановить базу из копии (с учётом WAL)

> Читайте раздел целиком до того, как что-то нажмёте. Здесь теряются данные.

### Сначала определите, какой у вас случай

**Случай А — кабинет открывается.** Восстанавливайте из кабинета: это безопаснее и делает всё правильно само.

**Случай Б — кабинет не поднимается.** Только подмена файлов по SFTP. Консольной команды восстановления в системе нет.

### Случай А: из кабинета (админ)

1. «Сервер» → список копий базы. У каждой — дата, время и вес. Копии снимаются раз в сутки, хранятся 14 последних.
2. Выберите ту, что заведомо старше момента поломки.
3. Нажмите «Восстановить». Система **сначала сама снимет копию текущего состояния** под именем `iigbot_ГГГГММДД_ЧЧММСС_before_restore.sqlite3` — если восстановились не туда, есть куда вернуться.
4. Восстановление идёт через SQLite backup API в то же самое соединение приложения: перезапускать процесс не нужно, ловить момент, когда база свободна, тоже не нужно. Кэш выгрузок система чистит сама.

### Случай Б: подменой файлов [SSH/SFTP]

1. **Снимите копию того, что есть сейчас.** Скачайте `_app/app/iigbot.sqlite3` вместе с `iigbot.sqlite3-wal` и `iigbot.sqlite3-shm` — все три файла. Даже повреждённая база может понадобиться, чтобы вытащить из неё что-то руками.
2. Возьмите файл копии из `_app/app/backups/` (имена вида `iigbot_20260817_2000.sqlite3`).
3. Переименуйте текущую базу: `iigbot.sqlite3` → `iigbot.sqlite3.broken`.
4. **Удалите `iigbot.sqlite3-wal` и `iigbot.sqlite3-shm`.** Это обязательный шаг. В режиме WAL свежие изменения лежат в файле-спутнике; если оставить старый `-wal` рядом с новой базой, SQLite попытается «дописать» к ней чужие изменения — в лучшем случае база не откроется, в худшем испортится молча.
5. Положите файл копии под именем `iigbot.sqlite3`.
6. Процедура 1 — перезапуск.
7. Откройте `/healthz`: должно быть `{"ok": true}`.
8. **ОБЯЗАТЕЛЬНО [SSH]:** переустановите вебхук бота:
   ```
   <ПРЕФИКС> webhook set https://reports.iig.ru/tg/webhook
   ```

### Почему шаг 8 обязателен и почему его нельзя пропустить

Секрет вебхука хранится **внутри базы** (`kv.tg_webhook_secret`). Старая копия несёт старый секрет. Telegram продолжает слать обновления с прежним заголовком, кабинет их не узнаёт и молча отвечает 403. Бот умирает абсолютно бесшумно: ни строки в журнале, ни ошибки на экране, ни тревоги. Пропустить этот шаг — значит починить кабинет и сломать бота, не заметив этого.

### Что ещё меняется вместе с базой — прочитайте до восстановления

| Что | Что произойдёт |
|---|---|
| **Метки планировщика** (`autosync_last`, `budgets_last`, `dialog_alert_last`, `backup_last`, `digest_last`) | Уедут в прошлое вместе с копией. На **первом же входе в кабинет** разом стартуют: синхронизация всех клиентов Директа, сбор бюджетов **с алертами в боевые чаты**, суточная копия, а в понедельник после 10:00 — **повторная сводка работодателю в Telegram**. Всё в одном процессе: кабинет будет тормозить 10–20 минут |
| **Секрет вебхука** | См. выше — обязательный `webhook set` |
| **Учётные записи и пароли** | Откатятся к состоянию копии. Заведённые позже сотрудники исчезнут, смены паролей отменятся. Заводите заново командами `useradd` / `passwd` |
| **История отправок `send_log`** | Откатится. Отчёты, отправленные после момента копии, из истории пропадут — но клиентам они уже ушли. Не перезапускайте из-за этого рассылку (раздел 13) |
| **Ключ сессий** (`kv.web_secret`) | Если копия старая — всех выкинет из кабинета. Просто войти заново |
| **Долги, уважительные причины, разметка таблиц** | Откатятся. Всё, что было проставлено после момента копии, придётся проставить руками |

**Как погасить лавину задач.** Либо предупредите всех, что ближайшие 20 минут кабинет медленный и часть уведомлений придёт повторно, либо **[SSH]** сразу после восстановления проставьте свежие значения меток в таблице `kv` — тогда планировщик решит, что задачи уже отработали, и ничего не запустит.

**Проверка, что починилось:** `/healthz` даёт 200 → кабинет открывается и показывает свежие данные → в чате `/whereami` отвечает → «Сервер» → «Проверить целостность» отвечает «ok».

## 12. Процедура 4: сервер потерян — развернуть с нуля

Когда применять: хостинг недоступен несколько часов, аккаунт заблокирован, файлы удалены. Порядок — по шагам, целиком занимает 1–2 часа при наличии всех доступов.

**Что нужно иметь на руках до начала:**

| Что | Где взять |
|---|---|
| Код приложения | Репозиторий `github.com/trutnevde/IIG-auto-reporter`. Секретов в нём нет |
| `secrets.json` (токен Яндекса и токен бота) | В репозитории **нет**. Только копия с прежнего сервера, либо перевыпуск (раздел 7) |
| `sa_key.json` (ключ Google) | Аналогично: копия или новый ключ из консоли Google Cloud |
| Копия базы | Последний файл `iigbot_*.sqlite3`, отправленный кнопкой в Telegram, либо скачанный из «Сервера». **Если внешних копий нет — данные потеряны целиком**, останется только справочник клиентов, который подтянется из Директа заново |
| Доступ к панели хостинга и к домену | Раздел 14 |

**Шаги:**

1. **Хостинг.** Аккаунт с поддержкой Passenger. Домен направить на него.
2. **Разложить файлы** так (раскладка обязательна: всё чувствительное лежит внутри `public_html/_app/`, закрытого от веба через `.htaccess` с `Require all denied`):
   ```
   ~/<домен>/public_html/
   ├── passenger_wsgi.py
   ├── .htaccess
   ├── tmp/restart.txt
   └── _app/
       ├── .htaccess          (Require all denied)
       ├── venv/
       ├── secrets.json       (chmod 600)
       ├── sa_key.json
       └── app/
           ├── app_config.json
           ├── iigbot.sqlite3
           └── iigbot/        (код пакета)
   ```
3. **`.htaccess` в `public_html`** — содержимое в `app/deploy/DEPLOY-beget.md`, раздел «public_html/.htaccess». Ключевое: `PassengerPython /usr/bin/python3` (системный, не venv).
4. **venv.** На Beget `python3 -m venv` не работает — нет ensurepip. Ставится так:
   ```
   python3 -m pip install --user virtualenv && python3 -m virtualenv --copies ~/<домен>/public_html/_app/venv
   ```
   Флаг `--copies` обязателен: симлинк на системный python в джейле запрещён. Пакеты: `flask`, `requests`, `gspread`, `google-auth`, `openpyxl`.
5. **Поправить пути** в `passenger_wsgi.py`: переменная `BASE` и версия python в пути к `site-packages` (сейчас там зашито `python3.10`) — под новый аккаунт и новую версию.
6. **Положить секреты** в `_app/`: `secrets.json` и `sa_key.json`.
7. **Положить базу** в `_app/app/iigbot.sqlite3` — **без** файлов `-wal` и `-shm`. Если базы нет, приложение создаст пустую и всё придётся заводить заново.
8. **Завести админа** (если база пустая):
   ```
   <ПРЕФИКС> useradd <email> <пароль> "Имя" --admin
   ```
9. **Поставить вебхук:**
   ```
   <ПРЕФИКС> webhook set https://<домен>/tg/webhook
   ```
10. **Завести задачи cron** в панели хостинга (в консоли Beget `crontab` отсутствует). Задачи и их команды — раздел 16 «Приложение сегодня» в этом же файле и живая справка `sysinfo.runbook`.
11. **Проверить по цепочке:** `/healthz` → вход в кабинет → `/whereami` в чате → `<ПРЕФИКС> gsheets-sync --check` → `<ПРЕФИКС> weekly --dry` (именно с `--dry`, иначе клиентам уйдут отчёты).

**Отдельно про Google-таблицы.** Они от сервера не зависят: ночная выгрузка живёт в GitHub Actions и продолжит работать, пока целы репозиторий и его секреты. Если потеряли и репозиторий — восстанавливать оттуда, откуда есть последний клон.

## 13. Чего в аварии делать нельзя

Пять запретов. Каждый из них — способ превратить частичную поломку в полную. Читайте до того, как начнёте чинить.

### 1. Не запускать недельную рассылку повторно

**Отчёты уйдут клиентам ЗАНОВО.** Идемпотентности нет: функция отправки пишет в `send_log`, но с этим журналом **не сверяется** (`iigbot/report.py`, `send_for_login`). Прогон без списка логинов берёт **все привязки агентства** (`run_weekly`). То есть второй запуск `weekly` = второй отчёт каждому клиенту, у которого есть привязанный чат.

Что делать вместо этого:

- Из консоли — **только** `<ПРЕФИКС> weekly --dry`. Режим `--dry` строит отчёты и печатает, что получилось бы, но клиентам не отправляет и в журнал не пишет.
- Боевую доотправку делать **только из кабинета**: кнопка «Переотправить недошедшим» (шлёт лишь тем, у кого в прошлом прогоне была ошибка) или «Отправить снова» в Истории — поимённо.
- Кнопка рассылки в кабинете шлёт **только своим клиентам** текущего пользователя, а не всему агентству. Консольная команда — всему агентству. Это разные вещи, и в аварии их легко перепутать.

### 2. Не открывать локальный кабинет с боевым `secrets.json`

**Он сам, без единого нажатия, начнёт писать живым людям.** Планировщик тикает из обработчика любого запроса — достаточно открыть страницу. Оттуда идут: сбор бюджетов **с алертами в личные чаты** и, в понедельник после 10:00, **понедельничная сводка работодателю в Telegram**. Все с боевым Telegram-клиентом.

Это не теория. В журнале `app/iig_errors.log` есть живые следы: строки вида `budgets.alert · не отправить в чат …` от 17 и 19 августа — попытки отправить в боевой чат с рабочей машины. Спас случайный сбой кодировки консоли Windows, а не какая-либо защита.

Правило: локальный запуск безопасен **только** если в локальном `secrets.json` подменён или пуст `telegram_bot_token`, и подменён он **до** первого запуска приложения. Копия базы безопасность не обеспечивает: база копия, а токен и чаты боевые.

### 3. Не поднимать бота локально

Токен у агентства один, вебхук и long-polling взаимоисключающи. Запуск `bot`, десктопного окна или `IIG_Запуск.bat` мгновенно ломает боевого бота — Telegram отдаёт 409 на `getUpdates`. Это самое вероятное неверное действие человека в панике: «проверю, живой ли бот, запущу у себя». Итог — бот, который до этого работал, замолкает у всех клиентов.

### 4. Не копировать базу файлами при работающем приложении

Включён режим WAL: свежие изменения лежат в файле-спутнике `-wal`, а не в самом `iigbot.sqlite3`. Кто заберёт один файл, получит **тихо устаревшую** копию — без ошибок, без предупреждений, просто без последних дней. Правильный способ — кнопка «Сделать копию» в «Сервере»: она сначала сливает WAL в основной файл, потом снимает целостную копию через штатный механизм SQLite.

### 5. Не восстанавливать базу «на всякий случай»

Восстановление — необратимая потеря всего, что произошло после момента копии: заведённых сотрудников, смен паролей, привязок, долгов, уважительных причин, разметки таблиц. Плюс лавина фоновых задач (раздел 11) и молча умерший бот, если забыть про `webhook set`. Восстанавливают тогда, когда база **действительно** повреждена — то есть когда `PRAGMA integrity_check` отвечает не «ok».

### И ещё три, помельче

- **Не редактировать `secrets.json` в редакторе, который дописывает BOM или меняет кодировку.** Токен превратится в мусор, и все пять API Яндекса откажут разом. В системе даже есть отдельная диагностика на этот случай: `gsheets-sync --check` печатает длину токена и признак ASCII.
- **Не удалять папку `backups/`, чтобы освободить место.** Это единственные копии базы на сервере.
- **Не менять день недельной рассылки, надеясь «дослать позже».** Период отчёта считается всегда как прошлая неделя Пн–Вс, независимо от дня запуска. Перенос на среду даст тот же прошлонедельный отчёт, а два запуска — два сообщения клиенту.

## 14. Кто что может починить и какие доступы для этого нужны

Здесь написано честно. Это не критика и не разбор — это то, что преемник обязан знать в первую минуту, а не выяснять на второй час аварии.

### Что может кто

| Роль | Что может починить сам | Где останавливается |
|---|---|---|
| **Специалист** (Ирина, Мария) | Привязать чат, «Отправить снова» одному клиенту, собрать «Сторонний» вручную, прочитать этот регламент (документ открыт всем ролям) | Всё, что требует SSH, панели хостинга и раздела «Сервер». Разделы «Журнал», «Сервер», «Пользователи» ей не видны |
| **Наблюдатель** (Ксения) | Видит всё агентство: все чаты, все проекты, Контроль, Бюджеты. Может отправить понедельничную сводку кнопкой. Читает этот регламент | Не может отправлять отчёты клиентам, не видит «Журнал» и «Сервер», не имеет SSH |
| **Админ в кабинете** (Денис) | Перезапуск, откат выката, копия базы и восстановление, проверка целостности, обслуживание, журнал ошибок, инвентарь ключей, справка по машине | Всё, что требует, чтобы кабинет вообще открывался |
| **Человек с SSH/SFTP** (Денис) | Абсолютно всё: подмена базы, откат руками, перевыпуск вебхука, заведение сотрудников, правка секретов, cron | — |

### Где сегодня узкое место

- **Доступ к серверу есть только у Дениса.** Пароль SSH и панели Beget на диске не хранится нигде — он живёт в переменной окружения на его личной рабочей машине. Ни в репозитории, ни в базе, ни в менеджере паролей агентства его нет.
- **Восстановление доступа к панели хостинга идёт на личную почту Дениса** (`trutnevde@gmail.com`), не на корпоративный адрес.
- **Второго администратора панели хостинга нет.** Значит, при недоступности Дениса нельзя: выкатить правку, завести или разблокировать сотрудника, перезапустить приложение, подменить базу, поставить вебхук, поменять расписание.
- **Репозиторий и его секреты** — под тем же личным аккаунтом GitHub.

Практический вывод для дежурного: если ваша проблема помечена **[SSH]**, а Денис недоступен, вы её не почините. Не тратьте время. Переходите к следующему пункту.

### Если человек с SSH недоступен дольше суток

1. Сообщите Ксении — решение о том, что делать с клиентами, за ней.
2. Отчёты за эту неделю доставляйте вручную: соберите текст в кабинете (если он жив) и отправьте клиентам сами, как это делается для «Сторонних». Если кабинет не жив — соберите цифры прямо в интерфейсе Яндекс.Директа.
3. Предупредите клиентов, что отчёт придёт позже. Молчание хуже задержки.
4. Восстановление доступа в панель хостинга — только через владельца почты восстановления либо через поддержку Beget с подтверждением владения аккаунтом. Это не делается за десять минут.

> **ТРЕБУЕТ УТОЧНЕНИЯ У ДЕНИСА:** кто второй человек с доступом к серверу и к панели хостинга; где лежит второй экземпляр пароля (корпоративный менеджер паролей?); на какую почту переключить восстановление панели; кто указан контактным лицом в поддержке Beget. Пока на эти вопросы нет ответов, весь раздел 14 сводится к одной строке «звонить Денису», и это и есть главный риск системы.

> **ТРЕБУЕТ УТОЧНЕНИЯ У ДЕНИСА:** телефоны и порядок эскалации — кому звонить первому, со скольких до скольких, и что делать ночью.

### Куда класть офлайн-копию этого документа

Копия должна лежать там, где её найдут все четверо и без кабинета. Разумный вариант — закреплённое сообщение в общем рабочем чате агентства, где есть все: обычным текстом первые три минуты и телефоны (чтобы читалось с телефона сразу, без скачивания), а полный файл `iig-reporter-docs-*.md` — вложением к тому же сообщению. Обновлять раз в две недели.

> **ТРЕБУЕТ УТОЧНЕНИЯ У ДЕНИСА:** какой именно чат агентства для этого используем и кто отвечает за обновление копии раз в две недели.

## 15. Где смотреть логи: пять мест, а не одно

Ни одно из них не показывает всю картину. В разборе инцидента обычно нужны два-три.

| Место | Что там | Как открыть | Кому доступно |
|---|---|---|---|
| **Кабинет → «Журнал»** | Хвост файла `iig_errors.log`, последние 300 строк, новые сверху. Формат: время, где, сообщение. Сюда пишут все фоновые задачи (`autosync`, `budgets`, `backup`, `digest`, `dialogs`) и упавшие методы кабинета | Пункт меню «Журнал» | Только админ |
| **Файл `iig_errors.log`** | То же самое целиком, плюс `iig_errors.log.1` — предыдущее поколение. Файл ротируется при росте больше 1 МБ, история хранится ровно за два поколения | **[SSH/SFTP]**, лежит в рабочей папке рядом с базой. Точный путь — «Сервер» → «Пути» → «Журнал ошибок» | Только с сервера |
| **Кабинет → «Журнал действий»** | Кто из людей что сделал: привязки, назначения проектов, долги, уважительные, заведение сотрудников, перезапуски, откаты, восстановления базы. Отвечает на вопрос «почему данные изменились» | Раздел «Контроль», блок журнала | Админ и наблюдатель |
| **Почта аккаунта хостинга** | Вывод задач cron: отработала ли недельная рассылка, что она напечатала. **Единственное место**, где видно, что задача вообще запускалась | Почтовый ящик аккаунта Beget | Владелец ящика |
| **GitHub → вкладка Actions** | Полный лог ночной выгрузки в Google-таблицы: что выгрузилось, что упало, с каким текстом | `github.com/trutnevde/IIG-auto-reporter` → Actions | Владелец репозитория |

**Как отличить «cron не запустился» от «у всех не было расхода».** Если задача не запускалась — в `send_log` (кабинет: «Отчёты» → «История») за этот день **не будет ни одной строки вообще**. Если запускалась, но отчёты не построились — строки будут, со статусом `skipped` и причиной. Разница принципиальная: в первом случае чините расписание, во втором чинить нечего.

**Чего в логах нет.** Обращений к Директу и Метрике по отдельности — сетевой слой их не журналирует, в `iig_errors.log` попадает только итоговый сбой операции. Успешных отправок отчётов — они пишутся не в журнал, а в таблицу `send_log`, и видны в Истории.

> **ТРЕБУЕТ УТОЧНЕНИЯ У ДЕНИСА:** на какой конкретно адрес падает вывод задач cron, кто этот ящик читает и что делать, если писем нет неделю.

## 16. Приложение сегодня: пути, команды, расписание

Точные пути, команды и содержимое базы **этой** машины система собирает сама. Не переписывайте их сюда руками — разойдутся при первом же переезде.

- **В кабинете:** «Документация» → «Живая справка по этой машине» (админ), либо прямая ссылка `https://reports.iig.ru/download/runbook.md` (тоже только админ).
- **В офлайн-копии:** та же справка подставляется последним разделом в файл `docs.md`, который скачивается кнопкой «Скачать всё одним файлом». Там она доступна любому вошедшему — то есть в аварии её увидит и специалист.
- **В кабинете, разделом «Сервер»:** блок «Пути» показывает то же самое на экране, плюс готовые строки задач cron с кнопкой «скопировать».

Что там есть: папка приложения, рабочая папка с базой и журналом, корень сайта, файл перезапуска, папка копий базы, папка копий выката, путь к ключу Google, версия Python, версия работающего кода и размеры всех таблиц базы.

### Две оговорки к этой автоматической справке

**Первая.** В блоке расписания справка пишет: «День и время недельной рассылки берутся из „Настроек“ кабинета». **Это неверно.** Поля «День рассылки» и «Время» в Настройках справочные и ни на что не влияют. Реально запуск задаёт строка задачи в панели хостинга Beget → Cron. Расписание в справке (`0 5` — обслуживание, `0 10 * * 1` — рассылка, `*/5` — проверка живости) — это **рекомендованный** текст, который генерируется из кода, а не считывается из панели. В `app/deploy/DEPLOY-beget.md` при этом указано «Пн 09:00» — третье значение.

**Вторая.** Справка говорит «раздел „Система“». В кабинете этот пункт меню называется **«Сервер»**. «Система» — только заголовок группы в меню.

> **ТРЕБУЕТ УТОЧНЕНИЯ У ДЕНИСА:** какие задачи реально заведены в панели Beget → Cron, с какими строками и в какое время. Из репозитория это не проверяется, а три доступных источника дают три разных ответа. Правильный порядок — открыть панель, переписать строки как есть и вписать сюда с датой сверки.

## 17. Журнал инцидентов

Заводите строку **в начале** инцидента, а не после. Через месяц никто не вспомнит ни времени, ни того, что именно нажимали. Этот журнал — единственный способ отличить «случайность» от «происходит третий раз, надо чинить причину».

| Дата и время начала | Что случилось (как это выглядело) | Кто разбирался | Что сделали | Сколько длилось | Причина | Что сделать, чтобы не повторилось |
|---|---|---|---|---|---|---|
| 19.08.2026 09:14 | *(пример)* Кабинет отдавал 500 после заливки правки | Денис | Откат выката из снимка 19.08-08.50, перезапуск | 22 мин | Опечатка в `api.py`, синтаксис не проверили до заливки | Добавить `ast.parse` в чек-лист выката |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |

**Как заполнять «Что случилось».** Пишите, как это выглядело со стороны, а не диагноз: «клиенты не получили отчёт в понедельник», а не «сломался cron». Диагноз идёт в колонку «Причина», и он может оказаться другим.

**Как заполнять «Сколько длилось».** От момента, когда сломалось (не когда заметили), до момента, когда проверка из колонки «как проверить, что починилось» прошла успешно.

**Что делать с журналом раз в квартал.** Пролистать. Две одинаковые строки — это не невезение, а нерешённая проблема: заведите на неё задачу и вынесите в план работ.
